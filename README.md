# FfbLatency — сравнение баз симрейсинга по времени отклика FFB

Инструмент для объективного сравнения двух DD-баз (Moza R21 и Simagic) по задержке
force feedback: от момента отправки команды до момента, когда руль реально тронулся.

## Как это меряется

```
[приложение] --DirectInput ConstantForce--> [USB] --> [MCU базы] --> [мотор]
      ^                                                                 |
      |                                                             [ротор+обод]
      +---- опрос позиции оси <-- [USB] <-- [энкодер базы] <-------------+
```

`t0` — момент вызова `SetParameters`, снятый по `QueryPerformanceCounter`.
`t1` — момент, когда ось действительно стронулась. Разница и есть измеряемая задержка.

**iRacing в измерительном контуре не участвует.** Его телеметрия идёт на 60 Гц (~16 мс
разрешение), а искомая величина — единицы миллисекунд, так что как источник timestamp он
не годится. Для сравнения двух баз он и не нужен: вносит одинаковую константу в обе цепи.
Реплей используется иначе — как источник реалистичного тестового сигнала, записанного
один раз и воспроизводимого идентично на обеих базах.

## Текущее состояние

| Компонент | Состояние |
|---|---|
| `FfbLatency.Analysis` — математика анализа | оценщик dead time готов, покрыт тестами |
| `FfbLatency.Spike` — проверка железа (этап 0) | готов, **на живом железе ещё не запускался** |
| `FfbLatency.Core` — работа с устройством | не начат |
| `FfbLatency.App` — WPF-интерфейс | не начат |

Сейчас задача одна: прогнать spike на Windows и понять, работает ли выбранный подход.
От его результата зависит устройство сэмплера, поэтому дальше без этих данных двигаться нет смысла.

## Требования

- Windows (x64), .NET 8 SDK — https://dotnet.microsoft.com/download/dotnet/8.0
- Подключённая и включённая база
- Свободный руль: на время step-теста он дёрнется усилием ~25%

## Перед запуском

**Закройте всё, что держит устройство** — иначе DirectInput не отдаст exclusive-режим,
без которого force feedback не работает:

- Pit House (Moza)
- SimPro Manager (Simagic)
- SimHub
- iRacing и любые другие симуляторы

## Запуск

```powershell
git clone git@github.com:sudri-code/iRacingBaseChecker.git
cd iRacingBaseChecker
dotnet run --project src/FfbLatency.Spike
```

Spike задаст пару вопросов: выбрать устройство, покрутить руль 5 секунд (для замера
частоты обновления оси), подтвердить step-тест.

## Что проверяет spike и как читать вывод

### 1. Exclusive-режим

```
SetCooperativeLevel(Exclusive|Background): OK
```

`FAILED` означает, что устройство занято другой программой — вернитесь к списку выше.
Без exclusive-режима FFB через DirectInput недоступен, и вся методика не работает.

### 2. Возможности устройства

```
FFB sample period:          ... мкс
FFB min time resolution:    ... мкс
```

Это заявленные характеристики самой базы. Их полезно сравнить между Moza и Simagic
ещё до всяких замеров.

### 3. Частота обновления оси

```
Интервал между отсчётами: медиана 1.002 мс ...
→ эффективная частота ≈ 998 Гц
```

Ожидается около 1000 Гц. Заметно меньше — значит база отдаёт позицию реже, и это
войдёт в измеряемую задержку как реальная её часть. Если частота сильно ниже,
разрешение метода упадёт, и параметры тестов придётся пересматривать.

Замер требует движения руля: значение оси меняется только когда руль крутится.

### 4. Стоимость вызова SetParameters

```
медиана 0.0123 мс, p95 ..., max ...
```

Этот вызов происходит внутри измеряемого интервала, поэтому его цена входит в результат.
Медиана заметно выше ~0.05 мс означает, что вызов блокирующий и потребуется систематическая
поправка.

### 5. Step response

```
#  0:   7.34 мс   (порог 3, шум 1)
...
Медиана: 7.10 мс, мин 6.20, макс 8.90
```

Главная проверка: виден ли отклик вообще и разумен ли порядок величины (ожидаются единицы
миллисекунд). Здесь используется простой порог — это ещё не измерительная методика, а
проверка жизнеспособности. Числа получаются завышенными; итоговый инструмент считает иначе
(см. «Точность» ниже).

Если движение не обнаруживается: проверьте, что руль свободен, а усилие в софте базы не
выкручено в ноль.

### 6. Параллельное чтение raw HID

```
→ \\?\hid#vid_...: ЧИТАЕТСЯ. Репортов 998, длина 64 Б, ≈997 Гц
```

Ключевой вопрос этапа 0: можно ли читать HID-репорты, пока DirectInput держит устройство
в exclusive-режиме. Если да — появляется независимый второй источник данных, которым можно
перепроверять замеры. Если нет — обойдёмся опросом через DirectInput, но кросс-проверки не будет.

## Что прислать по результатам

Весь вывод целиком, с обеих баз. Из него станет понятно четыре вещи: даёт ли база
exclusive-режим, какова реальная частота обновления оси, сколько стоит `SetParameters`
и виден ли step response.

## Тесты

Математика анализа не зависит от платформы и проверяется без железа — на синтетических
сигналах с заранее известной задержкой:

```powershell
dotnet test tests/FfbLatency.Analysis.Tests
```

## Точность оценки

Наивный порог не может сработать раньше, чем руль пройдёт целый квант энкодера, поэтому
он завышает задержку — и завышает тем сильнее, чем грубее энкодер. Две базы с разным
разрешением получили бы разное систематическое смещение, что обессмыслило бы сравнение.

Поэтому итоговый оценщик экстраполирует движение назад к нулевой скорости. Замеры на
синтетике:

| Квант энкодера | Порог | Экстраполяция |
|---|---|---|
| 1 | ошибка 3.00 мс | ошибка 0.11 мс |
| 4 | ошибка 4.00 мс | ошибка 0.41 мс |
| 16 | ошибка 7.00 мс | ошибка 0.15 мс |

Медиана по 200 повторам попадает в истинное значение с ошибкой 0.055 мс.

## Ограничения метода

- **Механика входит в результат.** У баз разная инерция ротора, плюс вес обода. Часть
  разницы будет механической, а не электронной. Честная формулировка результата —
  «сквозная задержка от команды до движения руля», а не «задержка электроники».
  Разделить их полностью можно только токовым датчиком на фазах мотора.
- USB polling (до ~2 мс в каждую сторону) входит в результат — это правильно, он реальная
  часть задержки.
- Практический потолок точности — около 0.5–1 мс из-за квантования HID-репортов и джиттера
  планировщика Windows. Разницу в 3+ мс метод различит уверенно, разницу в 0.5 мс — нет.

## Условия корректного сравнения

Замеры двух баз сопоставимы, только если совпадает обвязка:

- Один и тот же обод, физически переставляемый между базами
- Выключены damping, friction, inertia, natural friction/inertia, road sensitivity,
  FFB smoothing / reconstruction filter, torque slew rate limit, soft-stop
- Одинаковый угол поворота (900°), руль свободен, руками не удерживается
- USB напрямую в порт материнской платы, не через хаб
- Отключены USB selective suspend и энергосбережение USB root hub
- Зафиксированы версии прошивки и софта базы — они влияют на результат

Автоцентр приложение отключает само: это пружина, и она исказила бы step response.

## Разработка на macOS

Windows-проекты намеренно таргетят `net8.0`, а не `net8.0-windows`, поэтому компилируются
и на macOS — запускаются они всё равно только под Windows. Это позволяет ловить ошибки
компиляции без Windows-машины.

`FfbLatency.Analysis` и её тесты кросс-платформенные и полноценно работают на macOS.

Локальный `NuGet.config` в корне намеренно ограничивает источники одним nuget.org:
унаследованный из глобального конфига приватный feed отвечает 401 и ломает restore.
